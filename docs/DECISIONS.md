# Журнал решений Proba Intelligence Engine

Версия журнала: 0.1.0 · начат 2 ноября 2026 года · относится к контрактам 0.1.0.

Статусы записей:
- **принято** — согласовано владельцем;
- **выполнено** — действие уже сделано в репозитории и проверено (указано, как);
- **предложено** — рекомендация разработчика, ждёт подтверждения; до подтверждения применяется только к локальной разработке;
- **открыт** — вопрос владельцу, без ответа соответствующая внешняя операция заблокирована.

Изменения публичных контрактов (четыре схемы в `schemas/`) записываются сюда с новой версией и описанием миграции. Молчаливых изменений контрактов нет.

## 2. Решения

### D-001. Структура репозитория по манифесту — выполнено
Файлы перемещены в `docs/`, `prompts/`, `schemas/`, `examples/`, `config/`, `scripts/` без изменения содержимого. Проверка: `sha256sum -c MANIFEST.sha256` (36 OK, 2 отсутствуют), `scripts/validate.py` проходит. Новые документы (`DECISIONS.md`, `BACKLOG.md`) в манифест не входят; манифест описывает исходный пакет 0.1.0 и не переписывается.

### D-002. Технологическая основа — предложено
- Python **3.11+** (минимум выше 3.10 из пакета ради `tomllib` и стабильных типов; проверено на 3.13). Модульный монолит, пакет `src/proba/`, тесты `tests/` на pytest.
- Локальный срез: стандартный `sqlite3`, файл БД вне git (`var/`), ручной запуск через CLI `python -m proba ...`.
- HTTP API (FastAPI или аналог) — не раньше этапа ролей и рецензии; версия библиотеки фиксируется после проверки совместимости.
- PostgreSQL, фоновый worker с lease, мониторинг — до продакшн, не в локальном срезе. Отличия SQLite от продакшн фиксируются в README среза.
- Зависимости минимальны; каждая новая — с обоснованием здесь. Обязательных сетевых зависимостей у ядра нет.

### D-003. Публичные контракты и внутренние сущности — предложено
- Схемы 0.1.0 не меняются на этапах контрактов и локального ядра. Изменение — только через новую версию (0.2.0), запись здесь, миграцию примеров и тест обратной совместимости.
- Внутренние сущности без публичных схем, контракт которых определяется в коде и тестах: `User`, `RoleAssignment`, `PipelineRun`, `AgentCall`, `AuditEvent`, `PublicationAttempt`, `SearchLog`, `QAReport`, `ReviewPacket`, `UsageRecord`. Не представляются как покрытые четырьмя схемами.
- Причина отзыва, конфликты интересов (до G-3), поисковые строки — в `AuditEvent` и `SearchLog`.

### D-004. Хеш и целостность — предложено
- Единственная реализация `content_hash` в модуле `proba.contracts.hashing` строго по `docs/08` (SHA-256, UTF-8, сортировка ключей, `,`/`:`, `ensure_ascii=false`, `allow_nan=false`, LF, NFC, порядок массивов сохраняется). Эталон совместимости — результат `scripts/validate.py` на примере (`1c58fc9b…f564`).
- Хеш вычисляет только приложение; значение от модели или клиента игнорируется и перезаписывается.
- Серверная проверка ссылочной целостности: `article.source_ids` = объединение `claims[].source_ids`; каждый источник существует; каждый маркер `[claim:id]` в тексте указывает на существующее утверждение; утверждение без маркера в тексте — замечание QA (предлагается блокирующим для перехода в `in_review`).

### D-005. Версии Article — предложено
Каждая содержательная правка создаёт новую неизменяемую запись `(article_id, version)`; старые версии не удаляются и не перезаписываются. Запись требует `expected_version`; при несовпадении — отказ (оптимистическая блокировка). Review хранится отдельно и навсегда привязан к `(article_id, article_version, content_hash)`.

### D-006. Идентификаторы прогонов — предложено (закрывает A-1)
- `pipeline_run_id` — сквозной идентификатор прохода темы через конвейер; им связаны все шаги сценария приёмки из `03`.
- `agent_call_id` — один вызов роли; хранит `agent_id`, `prompt_version`, `model_id`, входные версии, длительность, токены, стоимость (`07`).
Поле `run_id` в оркестраторе и промптах означает `pipeline_run_id`.

### D-007. Машина состояний — предложено
Переходы Article выполняет только сервис, по явной таблице «из → в, кто, условия»; текст агента состояние не меняет. Проектная таблица:

| Из | В | Кто | Условия |
|---|---|---|---|
| briefing | research | editor / оркестратор | тема `active` |
| research | evidence | оркестратор | есть журнал поиска |
| evidence | drafting | оркестратор | карта утверждений валидна |
| drafting | qa | оркестратор / editor | схема и целостность (D-004) |
| qa | drafting | оркестратор | QA `needs_changes` |
| qa | in_review | оркестратор / editor | QA `pass`, назначен reviewer |
| in_review | approved / changes_requested / rejected | medical_reviewer (человек) | D-008 |
| changes_requested | drafting | editor | — |
| approved | drafting | editor | правка → новая версия, одобрение неактуально |
| approved | published | система после подтверждения CMS | действие publisher + шлюз D-009 |
| published | withdrawn | publisher | причина обязательна, история сохраняется |
| research / evidence / drafting / qa | research / evidence / drafting | editor | возврат с новой версией |

Каждая попытка перехода, включая отклонённую, пишется в `AuditEvent`.

### D-008. Роли и независимость решений — предложено (A-11 — см. Q-08)
- Роли: `owner`, `editor`, `medical_reviewer`, `publisher`, `service_account` (`03`). Роль `medical_reviewer` назначает только `owner` (человек) после проверки компетенции; сервисным учётным записям и агентам она недоступна технически, а не по соглашению.
- Review создаётся только сервером из аутентифицированного действия: `human=true`, `reviewer_id`, `article_version`, `content_hash`, `reviewed_at` ставит сервер; значения из запроса клиента игнорируются. `expires_at = reviewed_at + 30 дней` (`config/specialties.yaml`).
- `reviewer ≠ publisher` для одной версии (уже в конфиге). Предлагается также `reviewer ≠ автор/редактор этой версии` — ждёт Q-08.

### D-009. Шлюз выпуска — предложено (закрывает A-2)
Одна функция проверки допуска, вызываемая дважды: при действии publisher и непосредственно перед вызовом адаптера канала. Проверяет: роль publisher и его независимость; статус `approved`; совпадение `article_version` и пересчитанного `content_hash` с Review; `decision=approved`, checklist полностью `true`, нет `blocking_issues`; срок не истёк; нет утверждений `unsupported`/`disputed`; источники поддерживаемых утверждений `verified` и не `retracted`/`unknown` (D-014); `is_synthetic=false` у всех объектов. Действие publisher фиксируется как `AuditEvent` + `PublicationAttempt` с idempotency key `article_id:version:channel`.

### D-010. Export-only не является публикацией — предложено (закрывает A-3)
До выбора CMS выпуск ограничен preview/export в локальные файлы. Export не ставит `published` и не заполняет `publication`; материал остаётся `approved`, факт экспорта записывается в `PublicationAttempt(channel="export")`. `published` ставится только после подтверждения CMS с реальным URL.

### D-011. Синтетические данные — предложено (закрывает A-12)
Все выходы тестовых адаптеров имеют `is_synthetic=true` и маркер «СИНТЕТИКА» в текстовых полях. Шлюз выпуска отклоняет любой объект с `is_synthetic=true` независимо от рецензии. Синтетические источники не получают DOI/PMID.

### D-012. LLM и бюджет — предложено
- `external_calls_enabled=false` по умолчанию. Сетевой вызов разрешён только при одновременно заданных провайдере, модели, ценах, ключе в окружении и положительных лимитах; иначе — отказ до сети.
- Бюджет резервируется атомарно до вызова; повтор — максимум 2, исправление JSON — 1 в рамках того же бюджета; затем остановка и задача редактору.
- На этапах контрактов и локального ядра сетевой код не пишется вообще; тесты проверяют отсутствие сетевых обращений.
- Секреты только через окружение/хранилище; логи проходят редактирование; тест «ключ не попадает в лог».

### D-013. Аутентификация в локальном срезе — предложено
Локальное ядро доводит материал только до `in_review` и не создаёт Review. Поэтому до этапа ролей реальная аутентификация не нужна, а рецензия и публикация в локальном срезе отсутствуют, а не имитируются. Тестовые пользователи в тестах явно синтетические и не используются вне `tests/`.

### D-014. Источники — предложено (A-4)
- Дедупликация по нормализованному DOI (нижний регистр, без префикса `https://doi.org/`) и PMID; без них — ручное объединение редактором.
- Утверждение `supported`/`limited` допускается к выпуску только при источниках `verified`, `not_retracted`; `unverified`, `unavailable`, `retracted`, `unknown` блокируют выпуск (`unknown` — до разбора человеком).
- `abstract_only`/`metadata_only` обязательно отражается в `limitations` утверждения.
- Изменение записи источника создаёт задачу переоценки всех связанных версий; это не меняет хеш (см. Q-09).

### D-015. Хранение и аудит — предложено
`AuditEvent` — только добавление, без удаления и изменения. Локальная БД и экспорт — в `var/` вне git. Проектные сроки хранения (аудит 365 дней, временные извлечения 30 дней) применяются только после подтверждения владельцем (Q-03).

### D-016. Время — предложено
Хранение в UTC, RFC 3339 с часовым поясом на входе и выходе. Примеры с `+07:00` остаются валидными.

### D-017. Объём MVP и последующие этапы — принято, затем уточнено D-021
_Изменено 2 ноября 2026: языки, аудитория и порядок работ уточнены владельцем, см. D-021. Остаётся в силе: косметология первой, остальные направления позже, DeepSeek Super-Agent — отдельный эксперимент._
MVP (редакция 0.1.0): косметология, русский язык, профессиональная аудитория, одна редакция, один канал. Дерматология, гинекология, досье лизатов и бетулина, коммерциализация, экспорт, CRM — последующие этапы, отдельными решениями. DeepSeek Super-Agent — выключенный необязательный эксперимент, не зависимость MVP, без доступа к продакшн-данным, публикации и автоматическому слиянию.

### D-018. Язык — принято (`CLAUDE.md`)
Документация, интерфейс и сообщения об ошибках — по-русски; идентификаторы контрактов, кода и полей — по-английски.

### D-019. Проверка DeepSeek dsh-superagent-prototype — выполнено (исследование), использование в MVP не предлагается
Проверено 2 ноября 2026 года по первоисточнику: клон только для чтения коммита `6337fc8` (31 октября 2026) репозитория <https://github.com/deepseek-ai/dsh-superagent-prototype>, ничего не устанавливалось и не запускалось. Факты:
- репозиторий существует, лицензия MIT; README прямо называет его исследовательским прототипом, «не официальным продуктом DeepSeek» и «не готовым к продакшн»; публичная версия отличается от внутренней и от статьи о Super-agent;
- назначение — агент для разработки в одном GitHub-репозитории: слушает GitHub и, по желанию, Feishu, превращает разрешённые просьбы в задачи (Ticket), выполняет каждую в отдельной сессии-исполнителе и отвечает, например, pull request; есть веб-панель;
- архитектура «главная сессия (`orchestrator`/router) → исполнители (`worker`)» — это и есть обсуждавшаяся схема Router–Worker;
- работает только как плагин DeepSeek Harness (`@deepseek-ai/dsh`, MIT, «developer preview», обещаны несовместимые изменения), TypeScript, Node.js 22.19+;
- исполнители выполняют команды без подтверждения под учётной записью оператора (`danger-full-access`); документация говорит, что обёртки — не граница безопасности;
- нет учёта денежного бюджета, медицинского рецензирования, хеша версий и публикации в CMS.
Вывод: продуктовую часть Proba Intelligence Engine прототип не заменяет. Возможное применение — только как инструмент разработки, в изолированном эксперименте (шаг 10 `START_HERE.md`), после отдельного решения владельца. Заимствуем идеи, а не код: хранимые задачи с повтором (outbox), отчёты `ready/blocked/failed`, режим «сначала только записывать» (`observe`), панель «показывает только то, что ждёт человека».

### D-020. Несколько моделей в приложении — предложено
Для вызовов моделей внутри Proba Intelligence Engine используем собственный тонкий адаптер (D-012), а не фреймворк агентов. Роль → профиль модели задаётся в `config/models.yaml` (`routing`, `profiles`). У DeepSeek официальная документация описывает OpenAI-совместимый API (<https://api-docs.deepseek.com/>); совместимость Qwen с этим форматом в этом исследовании не подтверждена и проверяется перед выбором. Каждый провайдер включается только после Q-01.

## 2б. Смена приоритетов (2 ноября 2026, задание владельца)

### D-021. Новая главная цепочка — принято (владелец)
Цепочка: форумы и соцсети → запросы рынка → кластеры → контент X/Threads → научные источники → доказательные статьи → видео → обратная связь. Подробности — `docs/13_DEMAND_PIPELINE.md`. Языки источников не ограничены русским; аудитория — потребительская и профессиональная, раздельно. Медицинские границы `CLAUDE.md` не меняются. Задачи хешей и рецензии из прежнего backlog не удаляются, а переносятся в слой статей.

### D-022. Первый проход — на результатах веб-поиска — выполнено

### D-025. Черновики и статусы — предложено
Есть два статуса: `draft_no_medical_claims` и `research_draft`. Ни один не означает готовности к публикации. Перед выпуском нужны:
- отметка редактора по SHA-256 текста;
- для медицинских утверждений — отдельная отметка медицинского рецензента (другой человек);
- включённый канал и подключённый аккаунт.

Локальные отметки — не аутентификация, это временная мера до этапа ролей (B-030…).

### D-026. Контракт topic остаётся 0.1.0 — предложено
Задания на статьи проходят `topic.schema.json` 0.1.0: `language=ru`, `audience=professionals`, то есть статья для специалистов отвечает на вопросы, которые задают клиенты. Для статей на других языках или для потребителей нужна версия 0.2.0 схемы (Q-15). Молча контракт не меняем.

Созданы заново: в `.gitignore` — `.env`, `var/`, виртуальные окружения; в `.env.example` — пустые переменные. С `MANIFEST.sha256` они не совпадут: оригиналы не были загружены.

### D-028. Адаптер готовой выгрузки форумов `forum_export` — выполнено
`src/proba/demand/adapters/forum_export.py` читает `threads.jsonl` и `messages_all.jsonl` (формат выгрузки 2026-11-04). Одна `Discussion` — одна тема, сообщения в `comments` со ссылкой на тему. Поля берутся по белому списку; ники, профили и контакты не сохраняются, e-mail, телефоны и @упоминания в тексте маскируются. Метки подготовителя выгрузки хранятся отдельно (`export_labels`) и сравниваются со своей разметкой, а не принимаются как истина. Сообщение без темы или повтор темы — ошибка импорта.

### D-029. Сырые выгрузки форумов не попадают в git — выполнено
`data/raw/forums_*/` в `.gitignore`. В репозиторий идут код, агрегированные отчёты и метаданные без текстов (`data/meta/forums_ru_2026-11/`: summary, манифест SHA-256, отчёт валидации). Владелец просил «загрузить все файлы в репозиторий»; тексты сообщений оставлены локально по правилу этого же задания. Если нужно иначе — нужно отдельное явное решение владельца.

### D-030. Правила анализа сообщений — выполнено
`src/proba/demand/forum_analysis.py`:
- «актуальные» — сообщения 2024–2026, остальные — «исторические»; выводы о текущем спросе только по актуальным;
- исключаются: пустые, реклама и спам (своя разметка или метка выгрузки), постороннее, служебное, точные и близкие повторы (оригинал — более раннее сообщение); ответы представителей бренда и короткие реплики без вопроса остаются контекстом, но не считаются спросом;
- сегмент: признаки в тексте → редакционная метка выгрузки → площадка. На профессиональном форуме без признаков сегмент не угадывается (`unclear`);
- кластеры — по словарю понятий; «уверенность» не выше «средней»; топ тем и уверенность считаются внутри сегмента.

### D-031. Словарь понятий 0.2.0 — выполнено
Добавлены итальянские написания и кластеры C14–C21 (эпиляция, поставщики, бренды, цена, протоколы кабинета, обучение, возраст, состав и обещания). C01–C13 сохранили id и смысл. Миграция: первый проход 2026-11-02 (по заголовкам) не пересчитывался; при пересчёте возможны новые совпадения из-за расширенных шаблонов.

### D-032. JTBD и «что болит» — гипотезы — предложено
`config/jtbd_ru_2026-11.yaml` — черновик разработчика по прочитанным сообщениям. Не является наблюдением и не проверен автором-врачом. Пересказ без дословных цитат.

### D-033. Свежая выгрузка ChatGPT 2026-11-05 и объединённый отчёт — выполнено
Выгрузка `forums_ru_fresh_2026-11` (Пикабу 57 тем, PF-K 11 тем) проверена по манифесту SHA-256 и не пересекается с первой. `forum-report` принимает несколько `--data`; повтор темы между выгрузками — ошибка. Отчёт `reports/ru_market_2026-11` пересобран по обеим выгрузкам. Словарь 0.2.1: увеличение губ → филлеры (C04), изотретиноин и рубцы → акне, «сосуды» → розацеа, убраны ложные совпадения в «цене». Голос бренда в блогах компаний («мы в <компании> сталкиваемся…») размечается как реклама. Вордстат не получен (status blocked). Гипотезы JTBD 0.2.0.
